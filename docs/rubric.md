# Aspect Scoring Rubric

## Purpose

This rubric defines how free-text interview answers for `Junior Software Developer` roles are scored. Each aspect receives an ordinal score from `1` to `5`.

- `1-2`: weak
- `3`: acceptable
- `4-5`: strong

An aspect is considered weak if its score is `<= 2`.

## 1. Technical Depth

Definition: whether the answer demonstrates real junior-appropriate technical reasoning, implementation detail, debugging, tradeoffs, or constraints.

| Score | Description |
|---|---|
| 1 | No meaningful technical content. |
| 2 | Mentions technical terms or tools, but gives little real explanation. |
| 3 | Gives a basic technical explanation of the problem and solution. |
| 4 | Shows solid implementation, debugging, testing, decision, or tradeoff detail. |
| 5 | Shows strong junior-level depth with constraints, alternatives, evidence, or debugging detail without sounding like senior architecture ownership. |

## 2. Personal Contribution

Definition: whether it is clear what the candidate personally did.

| Score | Description |
|---|---|
| 1 | The candidate's own role is absent or hidden behind vague team language. |
| 2 | The candidate helped, but their exact contribution is weak or unclear. |
| 3 | The candidate describes a clear personal task or responsibility. |
| 4 | The candidate explains specific actions they personally took and how they collaborated. |
| 5 | The candidate gives a strong, credible account of their own contribution while staying junior-realistic. |

## 3. Clarity

Definition: whether the answer is understandable, concrete enough, and organized well enough to follow.

| Score | Description |
|---|---|
| 1 | Hard to follow, scattered, or missing the basic story. |
| 2 | Some understandable parts, but weak organization or vague wording. |
| 3 | Understandable with a basic situation/action/result flow. |
| 4 | Well organized, concrete, and easy to follow. |
| 5 | Concise, structured, specific, and very clear. |

## 4. Problem Solving

Definition: whether the answer describes a reasoning, troubleshooting, decision, or iteration process.

| Score | Description |
|---|---|
| 1 | No real problem-solving process is described. |
| 2 | Mentions a problem, but gives little reasoning about how it was approached. |
| 3 | Describes a basic troubleshooting or decision process. |
| 4 | Explains steps, evidence, alternatives, or tradeoffs used to solve the issue. |
| 5 | Gives a strong junior-level reasoning trail with tests, observations, iterations, or lessons. |

## 5. Impact

Definition: whether the answer explains the result, value, improvement, or learning that resulted from the work.

| Score | Description |
|---|---|
| 1 | No result, learning, or impact is stated. |
| 2 | A result is implied or mentioned vaguely, but the impact is weak or unclear. |
| 3 | Describes a clear result or learning outcome, but the impact is limited or not strongly supported. |
| 4 | Shows meaningful impact, improvement, or value for the project, team, users, or candidate growth. |
| 5 | Demonstrates strong and convincing impact, ideally with measurable outcomes, clear value, or significant learning. |

## 6. Role Relevance

Definition: whether the answer addresses the interview question and fits a Junior Software Developer role.

| Score | Description |
|---|---|
| 1 | Mostly generic, unfocused, or misses the requested interview angle. It may still mention a project. |
| 2 | Somewhat related, but indirect, incomplete, or focused on the wrong part of the experience. |
| 3 | Addresses the question in a basic but incomplete way. |
| 4 | Clearly addresses the question with a relevant junior developer example. |
| 5 | Directly and strongly answers the question with a well-matched junior project example. |

## Notes

- Scores should reflect evidence present in the answer, not generous inference.
- A fluent answer should not receive a high score if it lacks substance.
- Technology names alone do not justify high technical depth.
- Using `we` should lower personal contribution only when the candidate's own role is actually unclear.
- High technical depth for this project means concrete junior-level implementation/debugging detail, not senior-level architecture ownership.
